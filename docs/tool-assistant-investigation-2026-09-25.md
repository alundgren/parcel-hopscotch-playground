The main problem is how we describe the job and available actions to the assistant. The instructions mix an operator's job with the assistant's API, give incomplete guidance about when to call some tools, and leave the model to infer several product rules. Model capability also matters. Better instructions substantially improved several models; changing the model alone did not fix the original request.

The investigation's initial model recommendation was **GPT-5.4 with low reasoning for chat, keeping Jev for the existing decision tools**. It also recommended the tested operator instructions and revised batch and Undo descriptions. Mini is cheaper, but broader follow-up cases exposed errors that full GPT-5.4 avoided with the same instructions.

The subsequent implementation decision is to **retain Ministral 3B (`mistralai/ministral-3b-2512`) for chat and Jev (`typesafe/jev-1.13`) for constrained decisions while applying the application corrections**. This decision supersedes the study's chat-model recommendation for the current work. The GPT-5.4 measurements remain comparative evidence; they are not the configured application model or a production-selection claim. Keep server validation, previews, and human acceptance as application policy.

Three scouts inspected the request evidence, application behavior, and published guidance, then independently reviewed the model outputs. The initial model-comparison phase made **442 provider requests across 11 models**, including 221 turns through the actual server coordinator, and recorded **$0.4697191905**; six HTTP 429 responses had unknown per-call cost. The separate implementation phase later made 204 requests for **$0.014012910**, with no unknown-cost calls. Recorded costs sum to **$0.4837321005**; the final account balance was **$9.460403823**. These were exploratory comparisons and regressions, not independent tests of one recommended configuration.

The production instruction tells the assistant to use registered tools and start a matching tutorial for teaching requests. It gives almost no account of the operator's visible controls. The later experimental instruction improves the job description, but explicitly enumerates function identifiers. Neither provides a clear distinction between functions the assistant calls and controls the person uses. The captured authenticated context adds only the current view and focus. The model has to invent the missing introduction from those inputs.

This is visible in the experiments:

- Removing the function-name paragraph still left function names in all three Ministral operator answers. The definitions still supplied those names. Adding an audience rule alone also left function names in all three Ministral answers.
- Replacing the prompt with concrete operator facts kept function names out of all six onboarding answers across Ministral and Qwen, with the same 16 tool definitions. Some answers still invented behavior or omitted important steps. One Ministral answer introduced a shipping stage and a manual fix.
- GPT-5.4 Mini, using the original production prompt, selected a batch tutorial and a highlight call with an invented order ID. A stronger model followed a bad instruction more actively.
- In actual tool execution, Qwen and Mini sometimes prepared the full Ready batch after a request to pack one order. Mini also prepared a whole-receipt Undo after a request to undo one order. The tools described their scope but did not clearly say when the assistant must decline to call them.
- Adding call conditions to those two tool descriptions reduced broader preparations from **3/8 to 0/8** in the repeated boundary comparison. The combined tool-description and system-instruction variant also scored 0/8; there was no prompt-only arm. These are small samples that identify a useful correction, not a reliability guarantee.

The request format is valid enough for the tested models to make and complete real tool calls. Zero calls during general onboarding are appropriate. The problem is what the model says and when it chooses actions, not an obligation to call a tool on every turn.

Source review also found that some code-generated failures named the raw function identifier in user-facing copy. The current correction displays the registered human-facing purpose and a useful error while retaining implementation details in Audit. Prompt wording alone could not change this application-generated text.

A chat replacement can return a validated enum, but generated probability numbers do not establish calibrated confidence. The general setup I recommend follows seven principles:

1. **Give it the operator's job and the application's actual vocabulary.** Explain the normal workflow and important limits in a compact, versioned product description. Keep that content with the modules that own the behavior. Reuse actual labels and existing guide definitions where practical. Avoid a second manually maintained tool catalogue.
2. **Make every tool description answer when to call it and when to stop.** State scope, required evidence, prerequisites, and what success means. “Prepares all Ready orders” is weaker than “Call only after an explicit request for the full eligible batch; a subset request requires explanation and a new choice.” OpenAI and Anthropic both recommend clear tool purposes, inputs, conditions, and useful results. [OpenAI function calling](https://developers.openai.com/api/docs/guides/function-calling), [Anthropic tool design](https://www.anthropic.com/engineering/writing-tools-for-agents).
3. **Separate explanations, preparations, and commits.** General job questions need an explanation. Current-order questions need current evidence. An explicitly requested preview should be prepared. A mixed request to prepare and apply should receive the preparation plus a clear acceptance boundary. The application must enforce ownership, validation, versions, eligibility, and acceptance independently of model instructions. This app already has the essential commit protection.
4. **Keep critical outcome wording under application control.** Continue rendering exact previews, acceptance receipts, and the existing preparation acknowledgement from validated state. Give the fixed job introduction a maintained reference answer. Structured output can enforce fields and allowed values; it cannot prove that free-text fields contain true product claims. A second model that rewrites every answer would add another failure opportunity and another request; these results do not justify that design.
5. **Establish a capable-model baseline, then test cheaper replacements against it.** Keep the normal conversational tool loop bounded. A large tool catalogue alone does not justify another model call. Here, actual-source Ministral trials continued to fail common operator-help and scope cases, so the application now uses Jev for a narrow set of maintained replies before chat. Send mixed or action requests to the normal assistant, and count the extra provider call in latency, cost, and failure measurements.
6. **Evaluate complete work and complete answers.** Include no-tool explanations, legitimate actions, forbidden scope expansions, missing records, stale or accepted work, interface failures, and mixed requests. Check tool arguments, returned facts, final prose, and saved state. Track all requests, costs, retries, unknown billing, and time to completed work. A name-free answer, valid JSON, or a `complete` status is not sufficient evidence of success. [OpenAI agent evaluation guidance](https://developers.openai.com/api/docs/guides/agent-evals).
7. **Treat provider settings and routing as part of the tested configuration.** Specify reasoning deliberately, validate parameter support, and record the actual provider. One no-tool Qwen 3.5 9B call used default reasoning, consumed 4,096 reasoning tokens, and returned no visible answer after 44 seconds via Darkbloom. A tool-enabled call completed in about 3 seconds via Venice. Since tool presence and provider both changed, this cannot isolate tool-count effects or establish Qwen's general speed. OpenRouter documents reasoning-budget consumption and provider-specific tool support. [Reasoning controls](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens), [tool calling and routing](https://openrouter.ai/docs/guides/features/tool-calling).

## Initial model proposal and adopted application corrections

The study's GPT-5.4 candidate used `reasoning: { effort: "low" }`, `provider: { require_parameters: true }`, streaming, `max_tokens: 2048`, and `tool_choice: "auto"`. This was a tested request configuration for GPT-5.4, not a requested change to the current model. The application retains Ministral 3B for chat and Jev for constrained decisions and maintained-reply selection. Its chat request remains streaming, uses the existing 4,096-token output bound and automatic tool selection, and now sends `temperature: 0.1` with `provider: { require_parameters: true }`; it sends no explicit reasoning parameter. These are separate configurations and should not be compared as if the model were the same.

The current working-tree corrections retain Ministral and Jev while applying the product findings. A later actual-source 12-case Ministral run still exposed function names in general help, an unsupported subset-reversal promise, a false claim that physical packing had not occurred, and a queue summary that called Ready orders resolved where the record established only that packing was unconfirmed. One generic onboarding answer included a tutorial practice-group qualification. That qualification is supported by the app and is not counted as a factual error; its separate “flag for review” suggestion was unsupported. This run had no business commits and used simulated UI acknowledgements.

The current runtime adds one Jev selection call before each standard live chat turn. Jev can choose an app-owned general job guide, packing-scope or Undo-scope explanation, acceptance-only explanation, whole-queue summary, or one-order details reply. It receives trusted latest-receipt kind and size, so it can recognize “Undo just this order” as a subset or route an earlier-correction request away from a later batch. The app derives queue counts and order issue, evidence, recorded status, progress, and receipt details. Mixed requests, tutorials, filtered/grouped queue questions, complex evidence or consent, direct preparation, and whole-receipt Undo go to Ministral. Jev cannot prepare or accept business changes. Guidance mode and scripted fixtures retain their existing path; selection confidence is logged, not treated as calibrated.

An experimental 0.8 cutoff redirected valid 0.75 and 0.65 replies to Ministral, which reproduced weaker answers; the team removed it. The verified 18-case run scored 17 pass, 1 partial, 0 fail on an earlier source; its one partial misstated the first tutorial instruction. A separate eight-case review scored 5 pass, 2 partial, 1 fail, exposing omitted saved statuses and a reply offering a later batch when asked for an earlier correction. The app then added maintained statuses, a recognized earlier-correction no-preview route, and transactional receipt checks. These checks validate kind/count consistency and staleness, not inferred intent. A fingerprinted 26-case release scored 25 pass, 1 partial, 0 fail, with no material factual errors, unauthorized proposals, business changes, or internal-name leaks; its single partial retained jargon after a no-jargon request. A separately authored six-case holdout on that source scored 4 pass, 1 partial, 1 fail: a wrong proposal kind was rejected, but the model falsely promised a preview. No preview or business change occurred.

That holdout prompted two fixes: `getOrder` exposes the same operation-kind vocabulary as `prepareUndo`, and an unrecovered preparation failure ends with an app-owned failure acknowledgement unless a successful review was displayed. A later three-case test of the dual-ID version scored 2 pass, 1 fail: Ministral copied a UUID segment incorrectly on a single-address Undo; the failure acknowledgement truthfully reported the rejected attempt. The current model tool accepts only order ID plus expected kind/count and resolves the latest whole receipt; it cannot target a historical receipt. The order-ID-only `order-resolved` run matched the final app source and independently scored 3 pass, 0 partial, 0 fail. It prepared whole-receipt previews for a carrier order, a single address correction, and a six-change batch; all remained unaccepted with no business-state changes. This targeted three-case screen does not revalidate the 26-case release or six-case holdout.

The dual-identifier implementation was an intermediate design. It resolved the latest receipt from an order ID or selected a named earlier receipt by exact receipt ID. After the UUID copy failure, the model tool now accepts only order ID, expected operation kind, and expected change count. For an earlier-correction request, Jev has a maintained no-preview reply when it recognizes the request; the classifier can miss variants. Matching kind/count values is a consistency check, not proof of the person’s intent. Existing Undo version checks still prevent overwriting intervening work. The human Undo flow is unchanged.

- [agent-instructions.ts](../src/server/agent-instructions.ts) gives operator-facing workflow facts, direct-preview authorization, scope boundaries, evidence handling, and the acceptance rule. The prompt is shorter than the study's revision 6 but retains these behaviors. It cannot guarantee that live Ministral avoids identifiers or unsupported claims.
- [operator-replies.ts](../src/server/operator-replies.ts) defines the Jev choice contract. [agent-runtime.ts](../src/server/agent-runtime.ts) runs it before standard live chat. It supplies the trusted latest receipt kind and change count, selects maintained queue and single-order replies, or falls back to Ministral. Jev cannot prepare or accept a proposal.
- The [Work module](../src/modules/work/index.ts) owns maintained help and operational wording. `resolved` means a reviewed action was accepted, not that a carrier follow-up or duplicate hold is finished; `completed` means released to packing, not physical packing. Order details include a recorded status label, issue, evidence, progress, and the size of the whole receipt.
- The `prepareBatch` and current `prepareUndo` descriptions state call conditions and scope. The model Undo tool takes only order ID, expected receipt kind, and change count. The repository checks those values against the latest receipt in a transaction; existing version checks separately reject intervening edits. The tool always selects the entire latest receipt and cannot locate an earlier one. For an earlier-correction request when a later batch exists, Jev can select a maintained explanation and the runtime confirms that the latest receipt is a batch before returning it; the selector can miss other phrasings. During a tutorial, packing is limited to its assigned practice group.
- Preview acknowledgement tracking is cleared before each new navigation or presentation attempt and is restored only after a successful matching presentation. The runtime then uses the validated proposal kind and content to add app-owned next-step wording. A failed later UI operation cannot reuse an earlier preview acknowledgement. After a successful tutorial start or stop, the runtime reads current tutorial state and returns the recorded instruction; it does not claim that a target appeared.
- The registry preserves allowlisted domain recovery messages. Unexpected errors become a safe, generic message in model/operator history; their diagnostics are retained in redacted Audit records. After an unrecovered preparation failure, the runtime now gives an app-owned failure acknowledgement unless a valid preview was successfully presented, preventing the assistant from claiming that an absent preview is ready.
- When tool-result compaction removes order details, the runtime keeps the count, queue totals, each order's ID/status/family, and a note to read details before advising on evidence or resolution. It no longer reduces a compacted order list to generic success.
- The chat request uses automatic tool choice, a 4,096-token output bound, temperature 0.1, and `provider.require_parameters`, with no explicit reasoning setting. All 54 Browser Mode tests passed, including desktop and narrow layouts, before the final server-only Undo changes. All 22 E2E tests passed on the final source; build, typecheck, and guidance-boundary checks also passed. The 240-test full server run passed 239 tests and failed one existing one-second wall-clock assertion at 1266 ms. An isolated provider-audit rerun of 18 checks passed, including that assertion at 749 ms. All 240 unique server tests passed across the full run and isolated rerun; the full run itself was not clean.

Some behavior is deterministic: Jev labels map to app-owned text, queue totals come from stored order statuses, order details read one explicit or selected record, tool validation and receipt guards run in server code, proposal state follows UI acknowledgement, tutorial acknowledgement reads current state, and Audit stores redacted diagnostics. Jev still selects reply categories; Ministral handles tools and free text for fallback requests. Neither typed schemas nor prompts prove that free-text claims match the records. Evaluate category selection, answer accuracy, call scope, UI failures, provider availability, added cost, and saved state. Results from the 18-case test apply only to its older source revision.
For a maintained onboarding reference, the desired answer is approximately:

> Start in **Work**. Open an order and compare its recorded issue with the customer or operator evidence. **Review change** shows a preview: check the before/after values and consequences, then choose **Accept** or **Cancel**. Only your acceptance saves the change. Orders in the **Ready** queue still await release to packing. **Review ready orders** previews all currently eligible Ready orders together; check the inclusions and exclusions, then accept that batch to release them to packing. If an accepted change needs reversing, **Undo**, when available, prepares a checked reversal of the whole receipt. Review and accept that reversal too.

Two validation turns hit this key's OpenRouter limit of 20 requests per minute for Mini. The failures remain recorded, and interrupted cases were rerun with pacing. That is an availability result, not evidence of incorrect model reasoning. Keep retries bounded and respect provider backoff; do not silently change models and then report the result as the original configuration.

There is no evidence that leaving OpenRouter is necessary. The retained Ministral and Jev models, as well as the GPT-5.4 comparison candidates, completed requests through it. Direct APIs may offer different routing controls or richer replay support, but that is a separate comparison. Preserve provider-specific conversation metadata when adding models: Google's [thought-signature documentation](https://ai.google.dev/gemini-api/docs/thought-signatures) specifies replay requirements for Gemini tool calls. A simple Gemini 3.1 Flash-Lite loop worked here, even though the current adapter drops `reasoning_details`; that one success does not establish compatibility across its supported modes.
